# Hosted job discovery staging slice

This slice gives a signed-in **job seeker** a first list of matching employer jobs. It is disabled by default. It does not create a run, enqueue a browser task, or submit an application.

The official lead sync writes short-lived `VERIFIED` rows from operator-configured Greenhouse, Ashby, Lever, and SmartRecruiters feeds. `GET /api/jobs/matches?page=0` derives the candidate ID from a verified Cognito ID token. It reads that person's latest verified, reviewed profile artifact and filters leads by the saved target roles and locations. It then checks that each lead is open, unexpired, signed by the trusted writer's identity fields, and points to a recognized official employer posting. The response contains only the job title, company, location, provider, exact official link, verification time, and lead ID. No profile facts or résumé contents are returned.

Each page has at most ten jobs. Only pages 0–9 are allowed. The reader accepts at most four configured official sources with at most 50 current memberships each. It fails closed if a source exceeds that bound; a future global feed index should replace this bounded per-source read before scaling the catalog. Source URL and lead ID are never taken from the browser request. Source publication timestamps sort newer postings first when present, followed by verification time. The 15-minute lead expiry means feed sync must run reliably for the list to stay populated.

To stage, first enable the reviewed official lead sync with a source config of `maxJobsPerSource <= 50` and up to four sources. Build the onboarding Lambda after this change, then update the **staging** onboarding stack with `EnableJobDiscovery=true` and the same `OfficialSourcesJson`. The route remains absent unless that flag is true. Point the staging login Worker at the onboarding API, set `JOB_DISCOVERY_ENABLED=true`, and build the staging site with `OPENAPPLY_STAGING_JOB_DISCOVERY_ENABLED=true`. Test with a fresh verified profile submission; older staging profile markers lack `verifiedAtEpoch` and need to be resaved. Leave all flags off in production until reviewed and measured. No AWS change is made by this PR.

## Later standing-consent scheduler

The signed-in page is a preview of matching. A later scheduler must require a distinct, revocable standing consent record that states the target roles/locations, eligible sources, allowed application providers, and a daily application cap. Each tick should recheck the paid or approved-free entitlement, latest reviewed profile, deletion tombstone, consent version, active time window, and cap before creating any run. It should reserve a per-candidate per-day counter transactionally, create a deterministic run ID from candidate and official job key, and use the existing trusted run creator and queue admission path. On retry or crash, the same job key and run ID must resolve to the prior run. The browser worker must still stop at unsupported questions, authentication, CAPTCHA, and other handoff conditions; only an employer-confirmed receipt counts as a submission. Validate this with a monitored, consented beta before enabling automatic scheduling.
