# Hosted candidate onboarding, staging slice

The job seeker signs in with Cognito and enters career stage, target roles and locations, contact details, authorized countries, an explicit Yes/No sponsorship answer, and optional skills, education, work, and project facts. Each education, work, or project fact includes skill tags the seeker explicitly associates with that statement (`fact | skill 1, skill 2`); these tags are displayed with the fact on the review screen and copied unchanged into the approved claim. The résumé generator can select a work or project claim only when one of its reviewed tags matches the job description. Global skills alone do not label an unrelated claim, and neither the PDF nor the job description creates a skill tag. They upload a master résumé PDF and, optionally, a transcript PDF. The two PDFs must total at most 5 MiB. A review screen displays the exact entered answers and document names. Saving requires separate confirmations for accuracy, private storage and application automation. At least one education, work, or project fact is required for an application-ready profile.

The staging UI never extracts claims from a PDF. The API validates the separately entered facts and constructs `candidateProfileSchema` claims with `user-confirmed` status, allowed uses, and provenance bound to the reviewed onboarding submission. These are job-seeker assertions, not third-party verified facts. Sensitive work authorization and sponsorship are accepted only as explicit answers; demographic fields are not in this schema. Later PDF claim extraction must use the existing fingerprint and review flow in `src/candidate/intake.ts`. A saved profile is not a paid entitlement, job lead, application run or submission receipt.

`POST /api/candidates/onboarding` accepts only a same-origin request with a verified Cognito ID token and current paid or approved free entitlement. It checks the strongly consistent entitlement reader before parsing the upload body or writing storage; unreadable or expired access fails closed. API Gateway and Cloudflare still receive the request bytes before the Lambda gate, so their size limits and rate limits remain necessary. The service derives the job seeker's opaque UUID from issuer and subject, writes a pending marker, encrypts the PDFs and profile with a fresh KMS data key per artifact, and marks the profile verified only after every S3 write succeeds. The same transaction sets `applicationProfileReady=true` only when an approved structured application profile was stored; older onboarding submissions remain `false` and must be reviewed again before run admission. An idempotency UUID binds retries to a SHA-256 digest of the exact reviewed submission; a changed retry receives a conflict. The Lambda and Cloudflare Worker do not log request bodies or extracted content. `POST /api/candidates/plan` reads only the reconciler's entitlement table and reports active or inactive status; the browser cannot set it.

`deploy/aws/staging-onboarding.yaml` is a separate, **disabled-by-default** stack. It creates a staging-only KMS key, Lambda role, HTTP API and low-rate routes when `EnableOnboarding=true`. Its role can read/write candidate artifacts and profile markers and read entitlements. It has no Stripe secret, queue send or browser execution permission. The stack uses the existing private artifact bucket and run ledger. Build the package with `npm run build:onboarding-lambda`; publish that artifact to the staging code bucket, deploy the stack with the existing Cognito and storage identifiers, and set the staging login Worker's `ONBOARDING_API_ORIGIN` to its output. Build the site with `OPENAPPLY_STAGING_ONBOARDING_ENABLED=true` only after the API smoke test passes. Default build configuration leaves the candidate setup hidden.

Before enabling a beta, test a consented upload and retry against staging, verify KMS and S3 isolation, check delete/revoke behavior across pending and verified profiles, and confirm the job seeker can correct a saved profile. Existing minimal profiles need a new reviewed submission to become application-ready. Profile editing, withdrawal controls, broad file format support, PDF claim extraction, and a production deployment remain release gates. The separate deletion flow is described in `docs/hosted-deletion-staging.md`.
