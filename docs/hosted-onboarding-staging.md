# Hosted candidate onboarding, staging slice

The candidate signs in with Cognito and enters career stage, target roles and locations, school or employer, graduation or experience, work authorization and sponsorship. They upload a master résumé PDF and, optionally, a transcript PDF. The two PDFs must total at most 5 MiB. A review screen displays the exact entered answers and document names. Saving requires separate confirmations for accuracy, private storage and application automation.

The staging UI never extracts claims from a PDF. Entered answers are tagged `candidate-entered-and-reviewed`; later claim extraction must use the existing fingerprint and review flow in `src/candidate/intake.ts`. A saved profile is not a paid entitlement, job lead, application run or submission receipt.

`POST /api/candidates/onboarding` accepts only a same-origin request with a verified Cognito ID token. It derives the candidate UUID from issuer and subject, writes a pending marker, encrypts the PDFs and profile with a fresh KMS data key per artifact, and marks the profile verified only after every S3 write succeeds. The run creator reads only verified markers. An idempotency UUID binds retries to a SHA-256 digest of the exact reviewed submission; a changed retry receives a conflict. The Lambda and Cloudflare Worker do not log request bodies or extracted content. `POST /api/candidates/plan` reads only the reconciler's entitlement table and reports active or inactive status; the browser cannot set it.

`deploy/aws/staging-onboarding.yaml` is a separate, **disabled-by-default** stack. It creates a staging-only KMS key, Lambda role, HTTP API and low-rate routes when `EnableOnboarding=true`. Its role can read/write candidate artifacts and profile markers and read entitlements. It has no Stripe secret, queue send or browser execution permission. The stack uses the existing private artifact bucket and run ledger. Build the package with `npm run build:onboarding-lambda`; publish that artifact to the staging code bucket, deploy the stack with the existing Cognito and storage identifiers, and set the staging login Worker's `ONBOARDING_API_ORIGIN` to its output. Build the site with `OPENAPPLY_STAGING_ONBOARDING_ENABLED=true` only after the API smoke test passes. Default build configuration leaves the candidate setup hidden.

Before enabling a beta, test a consented upload and retry against staging, verify KMS and S3 isolation, check delete/revoke behavior across pending and verified profiles, and confirm the candidate can correct a saved profile. The current slice does not implement profile editing, withdrawal or deletion in the hosted UI, broad file format support, PDF claim extraction, or a production deployment. Those flows remain release gates.
